# AGENTS.md

Dendritic Nix flake (flake-parts + clan.lol) for the owner's NixOS machines
and Kubernetes tooling. Machines: `nixos` (Intel desktop, NVIDIA gaming), `kamrui-h1` (AMD dev
+ gaming desktop — KDE/Wayland, not a k8s box), `ghost` (Intel dev desktop), `hp-notebook`
(wife's Intel laptop), `nixos-installer` (ISO image). Public repo — secrets never go in git;
they live in sops / clan vars (`vars/`).

## Environment
- The dev shell is a devenv project shared by two entry points: `devenv shell` (CLI mode — evaluation caching, `devenv mcp`, auto-activation) and `nix develop` (flake mode — CI/flake consumers). Both import the same shared module `devenv/default.nix`; the root `devenv.nix` + `devenv.yaml` are the CLI entry, `flake-parts/devShells.nix` the flake entry.
- Activation (`devenv shell` or the auto-activation hook) loads `.env` via varlock (`bunx varlock load`), exporting `SOPS_AGE_KEY`, `GITHUB_TOKEN`, `TF_VAR_flakehub_token`, and sets `CLAN_DIR` to repo root (required by the `clan` CLI).
- `devenv.yaml` pins nixpkgs/nixpkgs-unstable/clan-core to the exact revisions `flake.lock` holds; `checks.devenv-lock-drift` fails `nix flake check` when they drift. When bumping those inputs, update `devenv.yaml` (and run `devenv update`) in the same commit. `devenv.lock` is committed; `.devenv/` is runtime state (gitignored).
- `.env` is gitignored (schema: `.env.schema`) and invisible to Nix evaluation — don't import it.
- Nix evaluates the flake from the git tree: `git add` new `.nix` files before `nix build` / `nix flake check` will see them.
- Formatter/lint gate: alejandra + statix + deadnix run as `checks.lint` (`flake-parts/checks.nix`), so `nix flake check` — and therefore CI — fails on findings. All three tools are in the devShell. Run before declaring work done: `nix fmt .` (bare `nix fmt` fails — it forwards only explicit args, so with no path alejandra reads empty stdin and exits 1, non-mutating; verify with `nix fmt -- --check .`), then `statix check .`, then `deadnix --fail .`. To fix mechanically: `statix fix .`, `deadnix -e .` (deadnix first when fixing — its `-e` leaves `{...}:` patterns that statix then wants as `_:`), then `nix fmt .`.

## Verify
- Local agent gate = CHEAP checks only: `nix build .#checks.x86_64-linux.lint -L` (alejandra/statix/deadnix — the same gate `nix flake check` runs) plus the lightest targeted build/eval that covers the change.
- HEAVY nix builds are deferred to CI (to be implemented at a later date — there is currently no CI): full `nix flake check --show-trace`, machine toplevels (`nix build .#nixosConfigurations.<name>.config.system.build.toplevel`), and `nix build .#documentation` (mkdocs-flake; also fails in-sandbox at plantuml — gradle daemon socket bind is policy-denied, PRE-EXISTING). Do NOT run these locally; note them as CI-deferred when reporting.
- VM tests live in `vm-tests/*.nix` (auto-discovered), exposed via `legacyPackages` so `nix flake check` does NOT run them. They need KVM — CI's job, never run them in the code-agent sandbox. Each test file gets 3 size variants (sm/md/lg) generated by `flake-parts/tests.nix`:
  - `nix run .#vm-test -- --list`
  - CI-style sandboxed: `nix run .#vm-test -- <name>-sm` (exit code = result, log is the build log)
  - Driver mode with artifacts: `nix run .#vm-test -- <name>-sm --driver` → `master.log` / `junit.xml` in `/tmp/home-vm-tests/<name>`; `--keep-state` (`-K`) keeps/resumes VM state; `--interactive` for the driver REPL.
- Docs (mkdocs-flake): `nix build .#documentation`; watch mode: `nix run .#watch-documentation`.

## Architecture
- `flake.nix` imports the entire `flake-parts/` tree via `import-tree` — new `.nix` files there are auto-loaded; no import list to update.
- `inventory.nix` is the machine source of truth (name, `deploy.targetHost`, tags). Clan imports `machines/<hostname>/configuration.nix` per machine. `inventory.json` is clan-managed install metadata — leave it.
- `machines/<name>/disko.nix` (disk layout, generated) and `facter.json` (hardware scan) must not be edited casually — disko changes require wiping/reinstalling the machine.
- Clan tags (`inventory.nix` → `clanServices/machine-type/`, `clanServices/tags/`) set `hostSpec.*` options — that's how hardware/desktop/networking gets attached per machine.
- Option namespaces: NixOS modules (`flake-parts/nixosModules/`) use `hostSpec.*`; home-manager modules (`flake-parts/homeModules/`) use `homeSpec.*`. The `default` modules auto-import everything except `profile-*` (per-user profiles in `flake-parts/homeModules/profiles/`, wired in `users/<user>/default.nix`).
- `lib.custom.relativeToRoot` resolves paths from repo root (`lib/`, exposed as `customLib`).
- `overlays/default.nix` adds `pkgs.unstable` (nixos-unstable) and routes service/agent packages into nixpkgs (`openshell`, `headroom`, `kimi-code`/`pi-coding-agent`/`claude-code` from the llm-agents input, ...); route new flake-input packages through it if machines need them as `pkgs.<name>`.
- The code-agent OCI image manages the pi/kimi/claude user configs via a standalone home-manager evaluation (`homeModules.profile-agent` + `homeModules.agents` + the sandbox module in `flake-parts/ociImages/code-agent.nix` — never hand-baked writeText+cp) and routes ALL agent inference through ONE baked, lazy-started headroom proxy per sandbox (`127.0.0.1:8787`). One proxy process serves every agent at once — one upstream per WIRE PIPELINE: Anthropic `/v1/messages` → api.anthropic.com (claude, pi's anthropic provider), OpenAI `/v1/chat/completions` → api.kimi.com/coding/v1 (kimi-code's native `type = "kimi"` wire). pi's Anthropic-wired kimi-coding provider rides the Anthropic pipeline with a per-request `x-headroom-base-url: https://api.kimi.com/coding` override — the proxy's SSRF guard resolves override hosts, but the gateway's interception DNS maps admitted hosts to fake 198.18.0.0/15 IPs, so the proxy runs with `HEADROOM_ALLOWED_BASE_URLS` naming exactly that URL (allowlist mode admits by name). `code-sandbox --inference <menu|all>` (default `all`) only selects which inference credential providers attach (kimi-for-coding / claude-subscription / claude-code / openrouter — `all` auto-attaches every menu provider present on the gateway except claude-code, which would shadow claude-subscription) — the image never changes per provider set, no per-sandbox agent dedication anymore. `/usr/local/bin/<agent>` wrappers run `headroom-proxy-ensure` (`--stateless --disable-kompress` — headroom-slim has no [ml] extra and huggingface.co is not admitted), refuse a STALE proxy from an older image generation (its `/health` Anthropic upstream must be api.anthropic.com), then exec the real CLI. The wrappers also pre-trust `/sandbox` folders (kimi `workspace-trust/` JSON records + claude `~/.claude.json` projects — both persist trust per absolute path, no wildcard) and give claude a per-session `--messaging-socket-path` (its cross-session socket-dir walk refuses `/`, owned by the VM host's overflow ids). Baked defaults: pi = kimi-for-coding @ max thinking + `defaultProjectTrust=always` (+ an anthropic provider that only works with the claude-code PLATFORM key — subscription tokens 429 on pi's raw-API shape; Anthropic bills subscription OAuth tokens only for Claude-Code-shaped traffic, no proxy setting reshapes that — + an openrouter provider on pi's NATIVE catalog, direct egress, no proxy: one `x-headroom-base-url` value can't serve the catalog's mixed `/api` vs `/api/v1` path layouts); kimi = k3 @ high effort, highspeed subagents, `default_permission_mode="auto"` (2.1.1: auto=Never Ask, yolo=Ask When Needed); claude = opus-5-5 + `permissions.defaultMode="bypassPermissions"`. NOTE the module-system footgun this fixed: `lib.mkIf c {...} // attrs` silently DISCARDS the //-siblings — use `lib.mkMerge` in home.file blocks.
- Steam/gaming lives in `nixosModules/jovian.nix` (`hostSpec.system.jovian.*`) — there is no separate steam module: steam is assumed with jovian, and every jovian machine runs the Valve jovian kernel (`pkgs.linuxPackages_jovian`).
- kamrui-h1 pins `linux-firmware` to the `nixpkgs-unstable` input (20260810) via a machine-scoped overlay: the 20260910 firmware's `yellow_carp_dmcub.bin` is rejected by PSP on its DCN 3.1.2 GPU (black screen; upstream reverted in 20260916, RH bug 2532947). Remove the overlay once clan-core's nixpkgs refreshes past 20260916.
- Secrets are clan vars: `vars/shared/`, `vars/per-machine/<machine>/`, produced by `clan.core.vars.generators` in the nixosModules. Use the `clan` CLI (e.g. `clan vars upload <machine>`); don't hand-edit encrypted `secret` files.

## Workflow
- Deployment is local: use `nixos-rebuild --flake /home/netsa/home#<host>` (shell aliases `nixos-rebuild-switch` / `nixos-rebuild-test` in `flake-parts/homeModules/shell.nix`), or clan's built-in deploy (`clan machines update`). The old FlakeHub `apply-*` packages and the `fh-apply` shell alias were removed together with FlakeHub publishing. GitHub Actions workflows were removed (recoverable from git history) — there is currently no CI (to be implemented at a later date); until then the local gate before pushing is `checks.lint` (see Verify — heavy builds stay CI-deferred).
- AI agents NEVER redeploy machines: no `nixos-rebuild` (switch/test/boot — any mode) and no `clan machines update`/clan deploy. Deployment commands in this repo are for the human's interactive session only; agents edit, lint and evaluate, then report the exact command for the human to run. The same rule covers clan vars: agents must NEVER run any clan CLI operation that changes sops secrets — `clan vars generate` and `clan vars set` are strictly human-interactive (and `vars set` cannot be used non-interactively anyway); the only agent-permitted vars operations are `clan vars list` and `clan vars get`.
- `code-sandbox` (devenv script) manages the OpenShell code-agent sandbox. Its policy (`openshell/policies/code-agent.yaml`) and the github-agent provider profile (`openshell/profiles/github-agent.yaml`) are TEMPLATES — `@bin_*@` placeholders rendered by the flake with the image's exact store paths (`packages.code-agent-policy` / `packages.github-agent-profile`, generator `flake-parts/openshellConfig.nix`) — each placeholder filled with the `readlink -f`-RESOLVED exe, because the supervisor matches `/proc/<pid>/exe` and nixpkgs `bin/` entries can be symlinks (pinning `nix`'s `bin/nix` symlink denied every nix egress). Never consume the templates directly and never hand-write store paths. `code-sandbox` also resolves the image BUILD SOURCE for rev pinning: `--flake REF` verbatim; otherwise the installable wrapper (`alwaysRemote = true`) ALWAYS builds from `github:external-systems/home/<remote HEAD>` (live repo head, never the stale baked store path, never a dirty checkout), while the in-repo devenv script is local-first (clean checkout at remote HEAD builds locally, else the remote HEAD); `--flake .` forces local. The policy/profile are rendered from the same resolved source as the image. `code-sandbox sync` (also run by `create`) drift-checks the gateway copy and pushes with `openshell profile update`; `code-sandbox doctor` reports profile/provider/sandbox health read-only. `openshell profile import` is one-shot — re-importing by hand is how gateway copies went stale (the github MCP server pin was lost this way). The script itself is generated by `lib/mkCodeSandbox.nix` (exported as `inputs.home.lib.mkCodeSandbox`) in three instances: the devenv script (`flakeRef "."` = this checkout), the installable `packages.code-sandbox`/`pkgs.code-sandbox` (baked with this repo's source — runs from ANY directory, no checkout needed), and the exported `flakeModules.code-sandbox` flake-parts module for other flakes (devenv projects pulling this repo use `inputs.home.lib.mkCodeSandbox` directly in their devenv.nix). Raw ssh and editor Remote-SSH (VSCodium server pre-baked; MS VS Code's server downloads via policy-admitted CDN hosts) are first-class: `create` appends a managed ssh config block to `~/.ssh/config.local` and passes the create-time `--env` set (`packages.code-agent-env`) that survives the supervisor's env scrub on every spawn path — the ssh/shell env model (no OpenSSH sshd; interactive = `bash -i` reading the baked `~/.bashrc`; exec = `bash -lc` reading `/etc/profile`; full terminfo incl. `xterm-ghostty`) is documented in `documentation/docs/openshell/code-agent-image.md` (Remote access) and the `sandbox-environment` skill.
- Only `x86_64-linux`.
