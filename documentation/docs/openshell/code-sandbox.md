# Code-Sandbox — Sandbox Lifecycle CLI

`code-sandbox` is one wrapper around the whole code-agent sandbox
lifecycle: build the OCI image from this flake, render the sandbox
policy + provider profile with the image's **exact store paths**,
drift-check them against the gateway, and create/attach/manage
sandboxes.
For what the image contains, see the
[Code-Agent Image user guide](code-agent-image.md); for the gateway
architecture, see the [OpenShell overview](index.md).

The script is generated by `lib/mkCodeSandbox.nix` — one generator,
three instances (below), so every entry point behaves identically.

## Getting it

| Where | What you get | `flakeRef` baked in |
|---|---|---|
| This repo's dev shell | the `code-sandbox` script | `.` (the enclosing checkout) |
| `packages.code-sandbox` → `pkgs.code-sandbox` (repo overlay) | an installable wrapper | this repo's source store path — **runs from any directory**, no checkout needed |
| `homeSpec.programs.openshell.codeSandbox.enable` (default `true`) | the wrapper on `home.packages` for every user with the OpenShell home-manager module | this repo's source store path |
| `inputs.home.flakeModules.code-sandbox` in another flake | `packages`/`apps.code-sandbox` configured by `perSystem.codeSandbox.*` options | the consumer's choice |

Host prerequisites: a Nix store (the wrapper builds the image with
`nix`), `git` (remote HEAD resolution), `yq` (profile canonicalization
in `sync`/`doctor`), and the host container engine's CLI (`docker` —
the loader copies the image into its store, then tags it). Plus,
checked with a fix hint rather than assumed: the `openshell` CLI
registered against a gateway, and the configured providers created on
that gateway (the `github-agent` profile and its provider must exist —
`code-sandbox sync` prints the exact `openshell provider create …`
line when one is missing). On the fleet's NixOS machines all of this
is in place (`pkgs.code-sandbox` rides the repo overlay; the gateway
module installs the openshell CLI and docker access for the VM
driver).

## Quickstart

```bash
code-sandbox                # build + load image, sync configs, create (name: code-<imghash>)
code-sandbox connect code-<imghash>
code-sandbox doctor         # read-only health report; exits 1 on findings
code-sandbox sync           # re-render + push profile if the gateway drifted
```

The sandbox name and the docker tag are both content-addressed
(`code-agent:<imghash>`), so an existing name always means an older
image and prompts for replacement (`-y` to skip the prompt).

## Subcommands

| Subcommand | What it does |
|---|---|
| `create` (default) | render policy + profile from the flake, `sync` them, build + load the image, create the sandbox, append a managed Remote-SSH block to `~/.ssh/config.local` |
| `sync` | render both configs from the flake; canonical diff against the gateway's copy of the provider profile (`openshell profile export`); push with `profile update` on drift (import only when missing); report provider presence + refresh status |
| `doctor` | read-only mirror of `sync` plus per-sandbox checks: attached providers, latest policy revision, and image staleness (sandbox name hash vs current image hash). Exit code = findings |
| `connect` / `exec` / `delete` | thin, predictable passes through to `openshell sandbox …` |
| `ssh-config` | append/replace the Remote-SSH config block for **all** active sandboxes (idempotent, comment-delimited) |

## Why sync/doctor exist: the drift lesson

The gateway admits a process's egress by matching `/proc/pid/exe`
against `binaries:` lists in the sandbox policy and attached provider
profiles. Those paths are nix store paths — they change on every input
bump. Hand-maintained globs drift silently: the github MCP server's pin
existed in git but not on the gateway, so its `api.github.com` calls
died with `EACCES` while `gh` (a different pin, still matching) kept
working.

The fix is generation: `openshell/policies/code-agent.yaml` and
`openshell/profiles/github-agent.yaml` are **templates** whose
`@bin_*@` placeholders the flake renders (`packages.code-agent-policy`,
`packages.github-agent-profile`) with the exact store paths of the
same package set the image is built from. `code-sandbox create` runs
the drift check on every invocation, so image and gateway config can
never disagree for long. Never `openshell profile import` by hand
after editing a template — imports are one-shot; that is exactly how
the original pin got lost.

Two rendering details matter. The paths are `readlink -f`-**resolved**
exes, not `bin/` symlinks: the supervisor matches `/proc/<pid>/exe`,
and nixpkgs entries like `nix`'s `bin/nix` are symlinks into other
outputs — pinning the symlink denied every nix egress (github tarball
fetches EACCES while git/curl worked). And the policy/profile are
always rendered from the **same resolved source as the image** (below),
never from a different ref.

## Image source: rev pinning (never "dirty")

The image bakes `Image: code-agent @ <rev>` — the flake's git
revision — into every agent's system-prompt briefing, so a running
sandbox can always be traced to the flake that built it. `create`
resolves the build source so that line never lies:

1. `--flake REF` given → REF verbatim (your choice; a dirty local ref
   pins `dirty`).
2. Otherwise the resolution depends on the instance:
   - **Installable wrapper (`pkgs.code-sandbox`, the home-manager
     module's instance) — `alwaysRemote = true`:** ALWAYS build
     `<remoteFlake>/<remote HEAD>` — the live public repo head, never
     the stale baked store path, never a dirty checkout. `--flake .`
     forces a local build.
   - **In-repo devenv script — local-first:** when the enclosing
     checkout is a **clean git tree whose HEAD equals the remote HEAD**
     → build the local tree (identical content, and the rev pins
     correctly); anything else → build `<remoteFlake>/<remote HEAD>`.
   - Generic consumers that set no `remoteFlake` get the warning and a
     local build.

`--flake .` forces a local build when you explicitly want one (expect
the `dirty` pin when the tree is dirty). `remoteFlake` and
`alwaysRemote` are generator parameters (`lib/mkCodeSandbox.nix` /
`perSystem.codeSandbox.*`).

## Options

```
-y, --yes                don't prompt when the sandbox already exists
    --cpu N              CPUs (default 4)
    --memory SIZE        memory (default 8Gi)
    --flake REF          build image/policy/profile from another flake
                         (installed wrapper default: the live
                         github:external-systems/home remote HEAD)
    --provider N         attach provider N INSTEAD of the defaults
                         (repeatable; defaults: github-agent kimi-for-coding)
    --no-sync            skip the profile sync before create
    --include-workdir    mount the directory you run this from into the
                         sandbox workdir (/sandbox)
    --no-include-workdir explicit default (clean, ephemeral sandbox)
    --no-ssh-config      don't touch ~/.ssh/config.local
    --ssh-config-file F  where to append the Remote-SSH block
```

`--include-workdir`: the rendered policy ships
`filesystem_policy.include_workdir: false`, so by default nothing from
your host directory enters the sandbox — clone inside it instead
(github.com is admitted read+write with the `github-agent` provider).
Flip the toggle when you want to work on local files directly: the
directory you invoke `code-sandbox` from is then mounted at the
sandbox's working directory (`/sandbox`).

## Using it from other projects

**Any directory on a machine that installed the wrapper** — this is
the default mode. `cd ~/anywhere && code-sandbox create` builds
everything from this repo's pins; your cwd does not need to be a
flake, a git repo, or have devenv.

**Another flake** (own image/policy, same lifecycle):

```nix
# flake.nix
{
  inputs.home.url = "github:andrewthomaslee/home";
  imports = [inputs.home.flakeModules.code-sandbox];
  perSystem.codeSandbox = {
    imageAttr = "my-agent-image";
    policyAttr = "my-agent-policy";
    profileAttr = "my-agent-profile";
    providers = ["github-agent"];
  };
}
```

```bash
nix run .#code-sandbox -- doctor
```

The consumer owns their policy/profile **templates** — copy the
`@bin_*@` placeholder pattern from `openshell/policies/code-agent.yaml`
and render them with this repo's `replaceVars` recipe
(`flake-parts/openshellConfig.nix`), so their store paths are
generated from the same package set as their image.

**A devenv project** (devenv can't consume flakeModules — call the lib
directly):

```nix
# devenv.nix — with this repo in devenv.yaml's inputs
{inputs, ...}: {
  scripts.code-sandbox.exec = inputs.home.lib.mkCodeSandbox {
    flakeRef = ".";  # or a baked ref for a from-anywhere wrapper
    imageAttr = "my-agent-image";
    policyAttr = "my-agent-policy";
    profileAttr = "my-agent-profile";
  };
}
```

**Reusable pieces for fully custom setups**: the generator is
`inputs.home.lib.mkCodeSandbox` (also inside the `mkLib` factory), and
`inputs.home.lib.mkLib ./.` binds the repo helpers to another root.
Everything the wrapper calls (`openshell` CLI, gateway, providers,
docker for the image load) is a host-level concern the subcommands
check for explicitly.
